# DedsiArche 前端

独立的 React 管理端基础项目，技术栈参考 DedsiNatives 的 react-admin。依赖版本于 2026-10-28 从 npm 官方仓库核实，使用稳定版。使用 Bun 管理依赖和执行脚本，提交 `bun.lock`。

## 启动

安装 Bun 1.4.2（与 `packageManager` 一致），保留 Node.js 22.13+（22.x）或 24+ 供工具链使用，推荐 Node.js 24 LTS。在仓库根目录执行：

```powershell
cd src/react
bun install --frozen-lockfile
bun run dev
```

访问 http://localhost:11126。进入系统需先登录，登录需要后端服务。

添加依赖使用 `bun add <包名>`，开发依赖使用 `bun add -d <包名>`。手动修改依赖后执行 `bun install` 并提交更新后的 `bun.lock`；CI 使用 `bun install --frozen-lockfile`。不再维护 `package-lock.json`。

需要覆盖默认配置时，将 `.env.example` 复制为 `.env.local`。浏览器直接请求 `http://localhost:11518/dedsi-arche-api`，可通过 `VITE_API_BASE_URL` 修改完整接口地址，不使用 Vite 代理。Axios 客户端位于 `src/services/http.ts`。

## 检查与构建

```powershell
bun run lint
bun run typecheck
bun run build
bun run preview
```

提供 development、prototype、test、production 模式，使用 `dev:prototype`、`dev:test`、`dev:prod` 以及对应的 `build:*` 命令。这里的 test 是环境模式，不是自动化测试。按需创建 `.env.[mode]`，所有模式默认使用相同基础配置。

构建产物位于 `dist`。生产服务器需要为前端路由配置回退到 `index.html`。构建时设置 `VITE_API_BASE_URL` 为浏览器可访问的后端完整接口地址，并在后端配置对应 CORS 来源。所有 `VITE_` 变量都会公开给浏览器，不应填写密钥。

TypeScript 沿用参考项目的双版本方案：`@typescript/native` 别名安装 TypeScript 7，使用其 `tsc` 构建；`typescript` 别名安装 TypeScript 6，供尚要求 `<6.1` API 的 typescript-eslint 使用。

保留 `oidc-client-ts` 依赖以对齐参考技术栈，尚未接入身份提供方或登录流程。当前已对接 Java 后端自己的 JWT 用户接口。

## 登录页面

访问 `/login` 查看独立登录页。页面使用项目 Logo、统一的蓝灰主题，支持账号密码、密码显隐、必填校验、加载状态及失败提示。当前后端仅支持账号登录，不显示第三方登录按钮。登录页不提供创建账户入口或忘记密码提示，账户由管理员在用户管理中新增。

登录调用 `POST /api/users/login`，成功后返回工作空间并展示用户信息。凭据仅保存在当前标签页的 `sessionStorage`，不保存密码；刷新页面可恢复未过期会话。请求自动附加 Bearer 凭据，访问令牌过期后清除本地会话，当前未实现自动续期。退出调用后端 `/api/users/logout` 撤销刷新令牌，成功后清理会话。所有系统页面（包括未知路径）均经过登录守卫。未登录、令牌过期或已认证请求返回 401 时清理会话并跳转登录页；登录成功后返回原站内路径。每次进入登录页都会清空当前站点全部 localStorage、当前标签页全部 sessionStorage 和内存会话；已登录时访问也保留在登录页，需重新登录。登录页不提供返回工作空间入口。前端守卫控制页面访问，接口权限仍由后端认证与授权校验。

联调需要启动 Java 后端及其数据库、Redis，浏览器默认直连后端 11518 端口。不能用界面演示替代真实认证。

登录表单只校验必填与纯空白，失焦和提交时给出字段提示，不校验账号密码长度或套用注册规则。账号提交前去除首尾空白，密码保持原样；提交时禁用表单以避免重复请求。开发及 preview 端口均为 11126。

后端 CORS 默认允许 http://localhost:11126 和 http://127.0.0.1:11126，其他跨域来源拒绝。前端直接请求后端，默认 VITE_API_BASE_URL=http://localhost:11518/dedsi-arche-api。

## 用户功能与真实测试

- `/register` 页面及路由已移除；后端注册接口保持不变。
- 当前用户资料统一由认证模块管理，随会话保存到 `sessionStorage` 的 `dedsi-arche.session.user`。登录、刷新令牌和刷新页面均复用完整资料；资料缺失时由登录守卫统一补取 `/api/users/me`，并发请求合并，失败可重试。
- `/`：复用缓存的当前用户资料；PATCH `/api/users/me` 修改姓名后更新缓存并同步侧栏。管理员修改本人后主动刷新资料，修改其他用户无需调用 `/me`。
- 用户、系统、权限列表从会话读取管理能力；搜索、翻页及刷新只查询业务列表。退出、过期或当前会话 401 清除缓存，旧会话请求不能写回新会话；后端仍独立鉴权。
- 账户中心的“延长登录”调用 POST `/api/users/refresh`，替换轮换后的两种凭据，同一时刻多个刷新操作合并为一次。当前采用手动续期，到期后重新登录。
- 账户中心和底部账户菜单均可退出。失败时保留会话供重试；成功时撤销刷新凭据并清理本地会话。
- 用户管理支持列表、新增、编辑名称和启停。管理员可重置密码、删除非管理员用户。

运行单元测试：`bun test`。启动真实后端和 PostgreSQL 后运行 `bun run test:e2e:api`，可通过 `E2E_API_URL` 指定后端。该脚本不使用 Mock，执行 26 项断言，覆盖六个用户接口及登录失败、校验失败、重复注册、刷新令牌轮换和退出撤销。每次创建独立 `api_e2e_` 测试用户，保留记录用于核对，不修改既有账户，不打印密码或令牌。

2026-10-29 浏览器端到端验收：未登录访问拦截 → 空注册表单 → 重复注册 → 新账户注册 → 错误密码 → 登录成功 → 查询资料 → 空白姓名拦截 → 保存姓名 → 侧栏同步 → 延长登录 → 折叠/展开 → 侧栏退出 → 未登录访问拦截 → 重新登录及页面刷新后资料保留。真实数据库核对测试账号姓名与会话撤销状态。
## 用户管理

管理员访问 `/users`，支持账号/姓名搜索、状态筛选、每页 10 条分页、新增用户、编辑姓名、启用/停用。保存前校验表单；停用需勾选确认，不能停用本人；并发编辑使用 version 检查，冲突后需刷新重试。列表不返回密码与令牌。

分页查询使用 POST `/api/users/page`，JSON body 包含 keyword、enabled、page、size（默认空关键字、不限状态、第 1 页、每页 10 条）；新增仍使用 POST `/api/users`，编辑仍使用 PATCH `/api/users/{id}`。管理权限由 `USER_ADMIN_USERNAMES`（逗号分隔的已存在账号）明确配置，默认没有管理员，公开注册不提供授予权限的字段。本机已按用户授权配置 `dedsi_user`。普通用户看不到菜单，直接访问管理页会提示无权限，调用接口返回 403。登录和 /me 返回 canManageUsers，服务端始终重新校验实际权限，不信任前端状态。

停用后后端拒绝该用户的 Bearer 请求，并撤销所有刷新会话。再次启用允许重新登录；原访问 JWT 若尚未到期，也会重新通过启用状态检查，因此启停不是永久撤销访问 JWT 的机制。

真实接口测试：设置 `E2E_ADMIN_USERNAME`、`E2E_ADMIN_PASSWORD` 后执行 `bun run test:e2e:users`。脚本创建独立 manage_e2e_ 账号并验证权限拒绝、查询分页、创建、冲突、停用、启用与会话撤销，不打印凭据。2026-10-29 第一轮通过 24 项断言；另完成真实浏览器新增、分页、编辑、停用确认、状态筛选、普通用户权限、停用后拦截和重新启用登录测试。
### 详情、删除与密码重置（2026-10-29）

操作列提供详情、编辑、重置密码和删除。新增/编辑复用同一个居中 Modal 表单；详情从 GET `/api/users/{id}` 实时读取。弹窗支持键盘焦点约束、Esc/关闭取消、提交中禁止重复操作。

DELETE `/api/users/{id}?version=...` 删除账户、刷新会话及用户岗位关联子实体，保留独立的岗位和权限定义。点击行内删除只打开二次确认，点击确认删除才发请求；取消不发送删除请求。当前账户及配置中的管理员不能删除，避免删除后注册同名账号继承管理权限。出现并发版本冲突时提示刷新重试。

POST `/api/users/{id}/reset-password` 接收 password 和 version，新密码按注册密码规则校验。通过独立 credential_version 使旧访问令牌与刷新凭据失效，不因普通资料编辑退出登录；重置本人密码后返回登录页。通过 V2 Flyway 迁移为已有用户/会话添加默认 0 的版本字段，保留既有账号和密码。

真实 API 脚本 `bun run test:e2e:users` 现通过 47 项检查，包含重置后的新旧密码、旧 JWT、旧刷新令牌、删除后不存在与登录失败。仅删除脚本本次创建的测试用户。浏览器真实验收包括 Modal 新增和编辑、详情、密码必填及一致性、旧会话失效、旧密码失败、新密码成功，以及删除取消和确认两个分支。测试中不重置或删除原有用户。

### 登录页视觉

登录页沿用后台蓝灰色系，宽屏为深海军蓝品牌区与白色表单区，最大宽度 1120px；1100px 以下收起品牌侧区。账号、密码使用可见标签，主按钮白字，密码显隐按钮保留可访问名称。仅调整布局与样式，保留原有账号密码登录、校验、跳转及错误反馈逻辑。

用户列表 POST `/api/users/page` 新增可选筛选参数 `phone`（最多 16 字符）和 `email`（最多 254 字符），自动去除首尾空白。支持普通文本部分匹配，邮箱忽略大小写；各筛选条件以 AND 组合，空条件不限制结果。列表和总数使用相同条件。搜索回到第一页，重置清空关键词、手机号、邮箱及状态并重新加载。


### 公共控件清空行为

Input 的文本、搜索、手机号、邮箱、密码及数字类型默认显示清空按钮（有值且可编辑时），不需要页面传 onClear。清空走原生 input 事件，再触发现有 onChange，兼容受控状态和 React Hook Form，保留 ref、失焦校验和焦点。onClear 仅为附加通知。clearable=false 可关闭；containerClassName 控制外层宽度，hasEndAction 为密码显隐等尾部按钮预留空间。
Select 默认可清空并通过 onValueChange 更新数据；默认清空为 ''，筛选场景可指定 clearValue='all' 回到全部。禁用、只读不显示清空按钮；业务上必须二选一的账户启停状态显式关闭清空，避免空值被转为停用。系统说明使用公共 Textarea。
搜索页不再单独传清空回调。清空条件仍需点击搜索后应用；整组重置逻辑保持不变。

统一 Form 现支持 input、select、textarea、date、multi-select、radio、switch、checkbox。新增组件的值类型、配置、键盘交互和校验示例见 [Form 文档](src/components/ui/form.md) 和 [完整组件示例](src/components/examples/FormComponentsExample.tsx)。不包含文件上传。

## 系统管理

管理员从左侧“系统管理”分组下的“系统管理”进入 `/systems`，页面为 [ManagedSystemsPage](src/pages/ManagedSystemsPage.tsx)。权限与后端 `userAdministration.canManage` 一致，沿用服务端 `canManageUsers` 能力标记作为菜单和页面入口判断，后端继续实施最终鉴权。

- 按系统编码/名称关键词、六种业务状态筛选，POST `/api/systems/page`，页码从 1 开始，每页 10 条；重置清空条件，删除末页最后一条后自动回退并重新加载。
- 新增 POST `/api/systems`；编辑前 GET `/api/systems/{id}` 读取最新资料，再 PATCH 保存并携带 version。代码全局唯一且不可修改，名称更改由后端在同一事务中同步相关权限、岗位及岗位权限子实体的系统名称。
- 详情 modal 展示 ID、编码、名称、入口、状态、排序、说明及创建/修改北京时间。前端不转换时区，ULID 作为字符串传递。
- 默认未上线、排序 0；正常状态必须有 HTTP/HTTPS 入口，禁止内嵌账号密码。名称/编码最多 100 字符、说明 512、入口 2048；排序为非负 Java Integer 范围。说明/入口清空时发送空串，避免 PATCH 的 null/省略保留原值。
- 删除二次确认后请求 DELETE `/api/systems/{id}?version=…`；被权限或岗位引用、或版本变化时拒绝删除；岗位即使未配置权限，只要归属该系统也会阻止删除。前端保留弹窗并提示。没有稳定错误码的删除 409 使用明确的联合兜底说明，不当成编码重复。
- 服务函数位于 [managed-systems.ts](src/services/managed-systems.ts)，表单与错误校验位于 [managed-system-validation.ts](src/lib/managed-system-validation.ts)。复用现有认证 HTTP 和全局消息，没有 mock 或 Vite 代理。

本次已完成静态契约核对及生产构建，未执行业务接口、浏览器或端到端测试。

## 权限管理

管理员通过“系统管理 → 权限管理”进入 `/permissions`，复用用户管理的列表、公共 Form、详情和删除确认弹窗。页面与服务端使用同一管理员策略，不将权限定义的启停当作用户授权。

- POST `/api/permissions/page`：按权限编码/名称/系统名称关键词、所属系统下拉选择（仅展示系统名称，提交编码精确匹配）、启用状态筛选，每页 10 条。搜索/重置回到第一页，删除后支持空页回退。
- 新增 POST `/api/permissions`：通过纯下拉框选择所属系统，调用专用 GET `/api/systems/options` 获取 code、name，以 code 作为 systemCode；不显示搜索框或分页栏，系统名称由后端读取，不发送可编辑 systemName。系统编码和权限编码创建后不可修改；权限编码在所属系统内唯一。
- 编辑前 GET `/api/permissions/{id}` 读取最新详情；更新为 PUT，发送 name、description、enabled、sortOrder 和 version。说明为空串时清除；编辑不发送不可变编码。
- DELETE `/api/permissions/{id}?version=…` 需要确认并携带详情版本。系统更名同步系统名称时会推进受影响权限及岗位的版本，冲突后需重新读取，不能覆盖提交。
- 编码/名称最多 100 字符，说明最多 500 字符，排序为 0～2147483647 整数，默认启用、排序 0；时间直接展示北京时间本地值。

实现入口：[PermissionsPage](src/pages/PermissionsPage.tsx)、[权限 API](src/services/permissions.ts)、[新增编辑表单](src/components/PermissionFormDialog.tsx)、[系统选择](src/components/PermissionSystemSelect.tsx)。后端未提供所属系统缺失的独立业务错误码，400 提示会同时提醒核对字段与系统是否已登记。


## 岗位管理

管理员菜单“系统管理 → 岗位管理”对应 `/positions`，复用用户管理的列表、筛选、分页、详情与表单弹窗。支持岗位编码/名称搜索、启停筛选、新增、编辑、详情及确认删除；时间直接展示后端北京时间。

编辑先调用 `GET /api/positions/{id}` 获取完整岗位与权限集合，详情失败时只显示重试，不初始化空权限编辑表单。保存通过一次 `PATCH /api/positions/{id}` 提交全部可编辑岗位字段、完整 `permissionIds` 和读取到的 `version`。空数组表示清空，编码创建后只读；系统与权限名称快照由后端生成，前端不提交这些展示字段。

权限选择按所属系统和关键词搜索，候选项分页加载；权限使用左右穿梭框：左侧搜索、系统筛选和分页，右侧显示全部已选；勾选后通过箭头批量添加或移回，也可清空已选。待移动项和已选集合独立于搜索结果，跨搜索与翻页保留。左侧隐藏已选项，分页总数仍按后端搜索结果（含已选）显示。详情初始选择来自服务端快照，停用权限在候选项中标明但仍允许选择。岗位与权限仅在点击保存后整体提交，关闭弹窗不写入。版本冲突保留输入并提示重读，不自动覆盖。权限定义改名后，后端在同一事务内同步岗位引用的权限名称并推进岗位版本；已打开的岗位编辑弹窗需要重新读取后再保存。系统更名同样由后端在同一事务内同步权限、岗位根实体及岗位权限子实体中的 systemName，并推进受影响聚合的版本。

岗位根实体包含 `systemCode`、`systemName`；列表及详情显示所属系统编码和名称，历史未归属岗位显示“未设置”。新增必须通过 `GET /api/systems/options` 纯下拉选择所属系统，选项只显示系统名称，提交系统编码。已归属岗位编辑时系统编码和名称只读；旧未归属岗位编辑时必须首次选择系统，绑定后不能改换。`systemName` 始终由服务端读取，不作为可编辑数据提交。岗位权限仍允许跨系统选择，岗位所属系统不会自动限制、清空或替换已选权限。

岗位被用户引用时，删除接口返回 HTTP 409 和 `POSITION_IN_USE`，前端明确提示先解除用户岗位关联，不将其误报为普通版本冲突。岗位删除成功时仅移除岗位及其权限关联，权限定义保留；用户删除则同时移除该用户的岗位关联，岗位定义保留。本次前端仅兼容删除保护与说明，不新增用户岗位选择界面。

### 用户岗位配置

用户新增、编辑表单使用左右岗位穿梭框：左侧支持岗位编码/名称搜索、分页及勾选本页，右侧显示全部已选岗位；通过中间箭头批量添加或移回，支持勾选全部和清空。跨页保留待移动项与已选集合，保存时只提交右侧岗位。左侧隐藏已选项，分页总数仍按搜索结果（含已选）显示。编辑先通过详情接口加载完整用户及岗位快照，再挂载表单；加载失败可重试，不会把列表摘要当作空岗位保存。

保存时用户资料、完整 `positionIds` 和编辑版本号整体提交；空数组清空岗位。四个快照字段只由服务端生成，重新提交集合会刷新快照。用户详情展示已存储的岗位编码、名称、系统编码、系统名称；旧岗位无系统时显示“未设置”。岗位选择不改变现有登录鉴权规则。

用户新增/编辑弹窗采用左右两栏：左侧基本信息，右侧用户岗位。两侧内容独立滚动，底部保存/取消保持可见；仍通过同一个表单整体校验与提交。

用户详情沿用编辑弹窗的左右分区：左侧基本信息，右侧用户岗位快照；岗位新增/编辑为左侧基本信息（含所属系统）、右侧权限选择。分区独立滚动，底部操作区保持可见，岗位和权限仍整体提交。

岗位详情同样采用左侧基本信息、右侧岗位权限的两栏布局，两侧独立滚动，底部关闭按钮保持可见，与岗位新增和编辑一致。

岗位新增/编辑采用更紧凑的基本信息区，状态与排序并排；权限穿梭框随弹窗内容区伸缩，列表独立滚动，搜索与分页固定在各自面板内。待移动项使用选中底色，并保留复选框和可访问的方向按钮。

用户新增/编辑同步采用紧凑弹窗尺寸与分区比例，岗位穿梭框自适应内容区高度，列表独立滚动；标题、选中底色、数量徽标和方向按钮样式与岗位编辑一致。

用户详情和岗位详情同步紧凑弹窗尺寸与左右比例，统一标题分隔、数量徽标及表格面板样式；两侧独立滚动，底部关闭按钮保持可见。
